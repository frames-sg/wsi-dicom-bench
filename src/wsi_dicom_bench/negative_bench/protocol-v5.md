# WSI-DICOM Negative Bench: October 22, 2026 amendment

This prospective amendment preserves manifest v4, expected-results-lock-v4.json, protocol-v4.md,
catalog v4, core profile v2, controls-v4, controls-v2, and adjudications-v1.json unchanged, so
studies pinned to catalog v4 keep their meaning. It adds catalog v5, core profile v3, manifest v5,
and expected-results-lock-v5.json for a `wsi-dicom` candidate whose validator adds seven VL WSI IOD
requirement families generated from the pinned DICOM 2026c DocBook tables (PS3.3 A.32.8 and the
Module and Macro tables it includes, PS3.6 Tables 6-1 and 7-1, PS3.10 Table 7.1-1):
`iod-modules`, `iod-attribute-presence`, `iod-enumerated-values`, `iod-vr-vm`, `iod-value-format`,
`iod-sequence-items`, and `file-meta`, each prefixed `intrinsic-wsi-dicom-2026c-`. Catalog v4 maps
none of these checks, and protocol v4 blocks release on any unadjudicated intrinsic failure, so the
candidate cannot be evaluated against v4.

Catalog v5 is catalog v4 plus one conformance-domain rule per new check (25 intrinsic, decoder,
and set rules; four observers). Profile v3 is profile v2 plus 13 IOD requirement rows (64 rows).
Catalog v5 requires the binary to declare rule set `wsi-dicom-general-v2` or
`wsi-dicom-core-profile-2026c-v3`; catalog v4 still requires `wsi-dicom-general-v1` or
`wsi-dicom-core-profile-2026c-v2`. A binary of one contract therefore cannot be scored against the
other catalog. The workbench defaults to catalog v5; catalog v4 and manifest v4 remain selectable.

The suite has 14 controls (15 objects), 10 development entries, and 149 evaluation cases. The 69
carried-forward cases keep their v4 mutations, seeds, source hashes, domains, and expected rules.
One harness correction changes generated bytes: the derived instance of NB-ID-006 now lists its
source in the Common Instance Reference Module (PS3.3 C.12.2), which the VL WSI IOD makes
Mandatory. The v4 handler omitted that listing, so the pair also lacked a required Type 1C
Referenced Series Sequence. The listing names the true SOP Class, so the CT class in Source Image
Sequence remains the only defect. The handler is shared, so regenerating v4 produces the corrected
pair as well; no v4 expectation depends on the listing.
The new `iod-structure-evaluation-v1` cohort has 80 deterministic single-defect cases. Each changes
one Data Element (one case changes a shared UID consistently at its three references), one
Sequence Item, or one File Meta element of a frozen control, at the top level, in nested Sequence
Items, or in Shared and Per-Frame Functional Group Items: 9 Module and Functional Group cases (an
absent mandatory Module; unlisted, misplaced, and missing mandatory Macros; Per-Frame Item count
above and below Number of Frames), 17 presence cases (Type 1 deleted and emptied, Type 2 deleted,
required 1C deleted and emptied, forbidden 1C present), 8 Enumerated Value, 12 VR and VM (explicit
VR controls), 17 Value format (UID leading zero, DA, TM, DT, lowercase CS, CR and LF in LO, DS over
16 bytes, IS over 12 bytes, PN components), 8 Sequence Item count, and 9 File Meta cases. Each case
records the exact attributes or bytes changed, its DICOM 2026c citation, and its expected rules.

Expectations for the IOD families were set by running the frozen candidate (`wsi-dicom 0.9.0`,
SHA-256 e4c5561ae73cf5a79c8186f8b78dd9ef1753b074495c8f7fec16bf50092e2b25) and adjudicating each
result against the cited DICOM 2026c text. They are not blinded. A new case expects the targeted IOD
rule and, where a catalog-v4 rule independently reports the same defect, that rule as well; no new
case has an adjudicated cascade. On a carried-forward case, an IOD-rule failure is an expected
failing rule when it reports the mutated Attribute or the inconsistency the case defines, and an
adjudicated cascade when it reports an unchanged Attribute or Module whose conditional requirement
the mutation changed. Every such decision, with the observed message and citation, is recorded in
the case's `iod_rule_adjudications`. Three carried-forward cases have new cascades: NB-CF-002 and
NB-CF-005 (Type 1C Attributes left present after their condition stopped holding) and CP-CF-002
(LABEL-conditional Module, Type 2, and Number of Frames requirements). For carried-forward cases,
`expected_unaffected_rules` is recomputed as every intrinsic rule that is neither expected nor an
adjudicated cascade; v4 had also listed the five pixel-decode cascades there.

The IOD families do not evaluate Context Group or Defined Term constraints, value constraints
stated only in prose (for example Bits Stored equal to Bits Allocated, Specimen Label in Image fixed
by Image Type, Number of Optical Paths equal to the Optical Path Sequence Item count), or conditions
undeterminable from the object, which are counted and never failed. Files with an absent or
unrecognized Transfer Syntax UID are excluded: the candidate cannot open them, reports only a Pixel
Data read failure, and emits no `file-meta` check, which the contract treats as an incomplete check
set. Scope remains VOLUME, TILED_FULL, one optical path, one focal plane, no extended depth of field,
and no concatenations; LABEL, OVERVIEW, THUMBNAIL, sparse tiling, source fidelity, calibrated
color, DICOMweb behavior, and compound defects remain outside this evaluation.

Acceptance is unchanged from protocol v4. Run with explicit `core-2026c` selection and the required
external validators dciodvfy, dcentvfy, and validate_iods (edition 2026c). Controls must pass every
required validator. Every negative case must fail all expected rules and its declared domain, and any
intrinsic failure that is neither expected nor an adjudicated cascade blocks release. A timeout,
launch error, unavailable required tool, output truncation, unmapped check, or incomplete check set
is an execution error and cannot count as detection. External-validator verdicts are observations,
not expectations. Report observed counts on the authored challenge; they are not clinical
sensitivity, prevalence, certification, or exhaustive normative coverage.

Normative sources: DICOM PS3.3 2026c [VL WSI IOD](https://dicom.nema.org/medical/dicom/2026c/output/chtml/part03/sect_A.32.8.html),
PS3.5 2026c [Data Element Types](https://dicom.nema.org/medical/dicom/2026c/output/chtml/part05/sect_7.4.html)
and [Value Representations](https://dicom.nema.org/medical/dicom/2026c/output/chtml/part05/sect_6.2.html),
PS3.6 2026c [Registry of Data Elements](https://dicom.nema.org/medical/dicom/2026c/output/chtml/part06/chapter_6.html),
and PS3.10 2026c [File Meta Information](https://dicom.nema.org/medical/dicom/2026c/output/chtml/part10/chapter_7.html).
